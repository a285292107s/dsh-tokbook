### D-001 · 2026-09-06 · 以外部双半区 Cordis 插件形态发布

**Status: current** · supersedes: — · superseded-by: —

**背景。** dsh-tokbook 必须不改 DSH 仓库就扩展 `web` profile。DSH 的功能都是 Cordis
插件,可带 client 半区;外部包无法使用单仓 `clientBundle()` 预设,也无法贡献生成的
Typert Remote。

**决策。** 一个包,两个半区:

- host 半区(`src/*.ts`)——监听持久化 `session/event` 流,拥有全部数据;
- browser 半区(`src/client/*.tsx`)——纯 slot 注册:`sidebar.footer.action` 触发按钮 +
  `shell.overlay` 浮窗;
- host→browser 数据走 feature-owned 精确 Fetch 路由
  (`ctx.webServer.register({ kind: 'exact', ... })`);
- client bundle 复刻懒加载 CJS factory,**绝不**在 client 入口加 `default` 导出
  (cordis loader 的 `exports.default ?? exports` 会掩盖 `.inject`,报 "without inject" 坏掉)。

理由与 DSH 机制背景:`docs/DESIGN.md` §3–§8。

### D-002 · 2026-09-06/07 · 逐请求账本行,而非每会话聚合

**Status: current** · supersedes: — · superseded-by: —

取代了 `docs/DESIGN.md` §5 第一期的「每会话聚合」框架(该文件的「重构说明」一节记录了这次变更)。

**背景。** DSH 内置的每会话投影太粗:回答不了按天/按请求的问题,格式一变就得重建。
参考项目 `dsh-token-usage` 按请求建行。

**决策。**

- 每条 **通道计费模型调用记一行 JSONL**——`assistant/message` 行以 message id 为
  去重键,外加 `compaction/summary` 与失败尝试(`turn/end` error、`llm/retry`)记成
  `kind: failure`(只计数、不计费)。
- 按**本地日历日**持久化:`usage-YYYY-MM-DD.jsonl`,追加 + 串行队列 + 进程级
  `requestId` 去重。
- **每个数据目录一个写入进程**,用 `owner.json` 标记强制(单写者守卫——风险在
  rollup/cache/refile 竞争)。
- 首次启动回填 + 手动重扫 = 重放 `sessionPersistence` 快照(幂等、去重安全),跨重启用
  持久化的 `sync-progress.json` 基线做增量探测。

现状形状:`docs/CONTRACTS.md`。跨模块级 HMR 重载的确切去重边界:`docs/HMR.md` §4。

### D-003 · 2026-09-07/08 · 成本层 + 价格表;额度只从官方 API 取

**Status: partially superseded** · supersedes: — · superseded-by: D-004, D-011, D-014

云端合并计价与规则链部分由 D-011 作废,额度卡的「三态」前提由 D-014 取代;
**额度只从官方 API 取**仍 current。取代了 `docs/DESIGN.md` §1 与 §11 中第一期的
「不做成本 / 成本属后续阶段」(「成本折算」风险行)。

**背景。** 账本要回答"这花了多少钱"——DSH 从不算钱;订阅额度 tab 要反映跨工具共享的
订阅价值——本地账本做不到。

**决策。**

- 计价 = ¥/M 每模型价目表,合并**云端镜像**(`pricing.ccsa.json`,启动时按
  `pricingRegion`/`pricingUrl` 同步)与手编 **`pricing.json`**(条目整体优先)。
- 每条记录按规则链 **时间规则 → 上下文档位 → 高峰时段**(上下文 ≈ input +
  cacheRead + cacheWrite)解析成 `RateKey`——只存身份、不存价格——所以改价在读取时
  重计价历史,无需重建账本/折叠。
- 价格表 tab 经 `GET/PUT /tokbook/pricing` 编辑手工层。
- 额度卡拉取各通道的**官方账户用量**(Command Code 的 CLI account 端点;OpenCode
  Go 的 `/zen/go/v1/usage`)——绝不本地估算;`quota-<provider>.json` 持久化最近已知
  `ok` 卡;`unconfigured`/`error` 卡即时重推、从不持久化。

落地:通道用量 + 额度的 commit `5e2c86f`(2026-09-07);pricing 手工编辑 tab 截至
2026-09-08 在工作区。

### D-004 · 2026-09-08 · （通道，模型） 双维计价 + 时间维度 + 双桶统计

**Status: partially superseded** · supersedes: D-003 · superseded-by: D-005, D-011

价格表整体重构(双维 / 覆盖层 / 云端)由 D-011 作废;**双桶统计**(`spend` /
`subscriptionValue`)继续有效,只是计费性质改为路由级手工声明。取代了 D-003 的「单 model
计价」部分(通道用量 / 额度与手工价格表本体仍在,承接其成本层语义)。

**背景。** 同一 model 串可能同时出现在官方 API 通道与订阅通道,计费性质与价格都不同;
前缀串(`deepseek/deepseek-v4-flash`)在基准价表查不到;厂商按记录时间调价。旧聚合身份
`(day, model, rate)` 会把两个通道的相同 (model, rate) 错并。

**决策。**

- 计价入口改为 `resolvePriced(provider, model, timeMs, context)`:
  该 record 的通道精确串在通道覆盖层命中(镜像 `provider-pricing.ccsa.json` +
  手工 `provider-pricing.json`,手工赢)→ `inheritBase` 走基准价表该 modelId 完整规则链,
  或 `segments` 按时间取段;否则回落基准价表 model 行;再没有 → unpriced(¥0)。
- 金额分双桶:`spend`(仅 `billing: 'metered'`,实际支出)与 `subscriptionValue`(仅
  `'subscription'`,订阅价值,非现金);`totalCost` 保留 = 两者之和,兼容旧 wire/旧 client。
- 聚合身份升级为 `(day, model, provider, rate)`;`byModel` 键改为 （通道，模型）;
  rollup 带 `schemaVersion: 2`,旧 v1 读作缺失 → 由日文件重建(不静默误并)。
- 价格表 tab 增加通道维度:查看 + 手工覆盖写回(PUT `/tokbook/provider-pricing`)。
- 镜像仓库(dsh-model-pricing)只负责云端两层数据;tokbook 只消费 + 本地覆盖,不做社区化维护。

落地:`PLAN.provider-pricing.md`(Phase 1–4)。完整推理见该计划与 `docs/DESIGN.md`。

### D-005 · 2026-09-09 · 手工价带时间维度;价格表 tab 显示"当前生效价"

**Status: superseded** · supersedes: D-004 · superseded-by: D-006, D-011, D-013

价格表不再有「手工层时间规则 / 峰谷」与层级概念;剩下的正是本条想要的**生效日期**,只是
简化为一条价段数组(D-011),`dailySlots` 想法由 D-013 以**用户自写**的形态带回。取代了
D-004 中「价格表 tab 只维护 flat 手工价」的 UI 部分(双维计价与双桶语义不变)。

**背景。** 厂商会调价:期限内/永久降价(云 feed 里 `deepseek-v4-pro` 的
"原价 → 第一次长期降价"、`glm-5.3-flash` 的"限时 5 折")与峰谷价(`deepseek-*` 的
"工作日高峰时段")。引擎一直支持 `timeRules` / `dailySlots`,但手工层只能写 flat 价,
价格表 tab 只显示云端的 `base`——于是带规则的模型在 UI 上显示的是**并不生效的价**
(如限时 5 折期间显示原价),而一次"自定义"保存就把整套调价史/峰谷静默抹平。

**决策。**

- `pricing.json` 条目允许两种形状:flat 价(旧格式)或规则集
  `{ base, timeRules?, dailySlots? }`。写回时无规则的条目仍序列化为 flat,保持文件可读、
  向后兼容。**整体替换语义不变**:手工条目替换该模型整套云规则。
- 手工层**不做上下文档位**(`contextTiers` 被忽略、UI 不编辑):需求只有调价史与峰谷,
  分档是云端 feed 的概念;云端带分档的模型在手工覆盖时会提示分档不再生效。
- 价格表 tab 的每行显示**当前生效价**(`PricingViewRow.now`,host 按读取时刻走
  「时间规则 → 峰谷」链算出),行可展开看完整时间轴;手工行可就地编辑调价时段与峰谷
  时段(含"该时段自己的峰谷"),保存前不生效、保存后全部历史按新价重算。
- 通道覆盖层:`segments` 支持**多段**时间轴(UI 逐段编辑),`inheritBase` 行显示
  跟随后的实际价;新增「新增覆盖」表单,可为镜像里没有的 （通道，模型） 建立覆盖。
- **同价通道(一跳路由别名)**:同一个套餐买多份时,每把 key 是独立路由(用量/额度必须
  分开),但价格与 `billing` 相同——复制 N 份条目会漂移,所以在 `provider-pricing.json` 的
  保留键 `$routes` 里声明一次 `{ "<路由>": "<被跟随路由>" }`。语义:**别名路由继承目标条目,
  自己的条目仍然优先**(显式条目 = 单独给这条路由调价的逃逸舱);只允许一跳,目标不能再是
  别名源(链/环在写路径拒绝),镜像 feed 不携带该键。实现上别名在读取合并时**物化**进表
  (`applyProviderAliases`),所以解析链仍是纯 （通道，模型）,UI 里继承行带 `via` 且只读。
  别名与条目共用同一次整表 PUT 与同一份脏状态。
- 保存按钮由**脏状态**(暂存草稿签名 vs 载入基线)驱动,而不是行数——删除最后一条手工
  覆盖是合法编辑(空表 = 清空手工层);脏草稿跨挂载存活(切 tab / 关浮窗不丢)。
- **入口按用户的问题组织**:默认视图是「在用」——账本记过的模型串平铺一张表(按用量降序),
  每行给当前生效价与来源,编辑时不会跳分组;「价格未知」「全部」是另外两档筛选(手工价/云端
  是「全部」里的分组,不再各占一个筛选)。模型层没有条目但覆盖层定价的串,直接显示覆盖层
  解析出的价,动作是「去覆盖层」(深链到那条覆盖)——给这类串写模型层条目永远不会被读取。
  保存被拒时滚动定位到错误条与出错行。
- **默认只读,改价是显式动作**:这个 tab 主要被用来"看",改价是低频事件——所以手工行平时是
  只读摘要(价格 + 来源 + 生效窗口),点「编辑」才把四档单价变成输入框并展开规则编辑器,
  同一时刻只有一行可写(与通道面一致);删价收进编辑态的「删除手工价」。同时把低频的
  「同价通道」「新增覆盖」收进列表下方的「高级」折叠。目的:首屏只剩「搜索 + 一张表」,
  而不是"报表与表单同屏"。术语也向用户语言收敛(跟随基准/自定时间轴/占位 → 跟随官方价/
  自己填价/先按官方价),「跟随官方价」的模型 id 改为带候选列表的输入(可手填,但不必凭记忆)。
- 同一模型的 `timeRules` **不得重叠**(写路径拒绝、读路径按 `startTime` 排序):引擎取首个
  命中,重叠会让"看到的"与"生效的"不一致。未保存草稿在价格表 tab 上以小圆点提示,**并且
  逐行标出**:改过的行标「未保存」、被删掉的手工价标「待删除」——脏状态由逐行签名与基线
  比对得出(行序变化不算改动,暂存删除也不会因为行消失而不可见);Ctrl/Cmd+S 在可见的那
  一面保存;窄屏(≤640px)价格表行改为堆叠布局,四档价各自带标签。

落地:`src/pricing.ts`、`src/types.ts`、`src/client/PricingPanel.tsx`、`src/client/store.ts`、
`scripts/smoke.ts`;契约见 `docs/CONTRACTS.md`,推理见 `docs/DESIGN.md` §3。

### D-006 · 2026-09-09 · 价格表云端参考表按厂商分组;通道维度留在覆盖层

**Status: superseded** · supersedes: D-005 · superseded-by: D-007, D-011

云端参考表与厂商分组随云端一并删除(D-011)。取代了 D-005 中「全部」视图里云端基准价表
平铺展示的 UI 部分(双维计价、双桶统计与编辑语义都不变)。

**背景。** 「全部」里的云端基准价表是 185 行平铺的模型串（真实数据），是这个 tab 最不可扫的
一屏——用户要"理解"的不只是价格，还有"这是谁家的模型"。而 feed 的每个模型本来就带
`family`（厂商：gpt 38 / claude 17 / qwen 17 / deepseek 9 / glm 9 / …），
`coerceCloudPricing` 之前把它丢掉了。

**决策。**

- 云端 feed 的 `family` 透传到 `PricingViewRow.family`（别名行带其所属模型的 `family`；
  feed 没命名的串没有该字段）。**只作展示元数据，不参与计价链**。
- 「全部」的云端参考表按 `family` 折叠分组：模型数降序、未标注厂商的串最后，组默认折叠，
  搜索自动展开命中的组。分组只是折叠一层，不改变任何行的定价与编辑动作。（未标注桶刻意叫
  「未标注厂商」而不是「其他」——`other` 是 feed 里一个真实的 `family` 值。）
- 两个角色轴（模型厂商 / 通道）**不混进同一棵树**：厂商（`family`）用于云端参考表的浏览分组；通道
  路由的展示与编辑归属留在既有的 **通道覆盖层**与通道用量 tab。原因：
  模型层价格是**全局**的（`pricing.json` 是 `Record<model, 规则集>`），同一个串可能被多条
  路由计费（本机：`deepseek-v4-flash` 在 deepseek-official 与 opencode-go、`glm-5.3-flash`
  在 opencode-go 与 zai），按路由分组会让同一行在多组里重复出现、而编辑只影响那份全局价。
- 「在用」列表按通道路由分组是**紧随其后的第二步**（已与维护者确认：共享串只在主通道
  可编辑，其余通道只读并标「全局价」）。它需要先把 `pricingView()` 的 `UsedModelHint`
  键从模型串改成 `(provider, model)`，所以与本次展示分组分开落地。

落地：`src/pricing.ts`、`src/types.ts`、`src/client/PricingPanel.tsx`、`src/client/styles.ts`、

### D-013 · 2026-09-11 · 价段时间轴升级为两级:整点生效 + 每日时段(峰谷)

**Status: partially superseded** · supersedes: D-005, D-011 · superseded-by: D-020

取代了 D-011「价段 = 四档价 + 生效日期」中的时间轴部分(单手工表、路由卡、`$billing`、
卡片并集全部不变),并把 D-005 的 `dailySlots` 想法以**用户自写**的形态带回。本条
「界面层同日修订」里**模型行显示两个身份**的做法已由 **D-020** 取代(行上只显示一个);
其余(时间轴、峰谷、写路径放宽、排版实测)不变。

**背景(维护者原话)。** 「用户首先输入价格生效时间点,时间可以精准到小时。然后输入时间段,
几点到几点,这个时段是什么价格。」D-011 的价段只有一个维度(生效日期 + 四档价),写不出官方
的峰谷价:DeepSeek 是「闲时价 + 工作日 9–12 / 14–18 高峰翻倍」,而官方调价公告本身就发生在
12:00 这种整点上。

**决策(经维护者逐项确认)。**

- **两级时间轴**:价段 = **生效时刻**(本地 `YYYY-MM-DD`,或**整点** `YYYY-MM-DDTHH:00`;
  省略 = 最早一段)+ 四档**全天价** + 可选的**峰谷时段**数组。取价 = 先按记录时间戳取生效段,
  再在该段内按记录**本地星期几 + 小时**取生效时段;没被任何时段覆盖的时间按全天价算。
- **「全天价 + 峰谷时段」而不是「时段铺满 0–24」**:普通调价只填一个全天价(界面上写着
  `00:00–24:00`),峰谷只加高峰那几行;空隙的含义天然唯一,不需要写路径去拦「有空隙」。
  时段左闭右开,`0 ≤ start < end ≤ 24`。
- **时段带 `days`(`daily` / `weekdays` / `weekends`)**:官方高峰只在周一至周五,不区分
  工作日会把周末按高峰价高估。冲突判定 = 区间相交**且** `days` 有交集。
- **时段身份 = `start` + `days`**(不是索引、也不是 `(start, end)`):该二元组在同一段内唯一,
  所以改**费率或结束小时**就地重算历史,不像 `(start, end)` 那样一改结束小时就把历史打成 ¥0。
- **悬空身份要浮出来,不能静默计价**:改掉某时段的 `start` / `days`、或删掉它之后,那段历史的
  费率行身份就不在表里了——`priceOfKey` 返回 null(¥0)并把这些模型并入 `unpricedModels`。
- **规则只写一遍**:`src/price-format.ts`(纯模块)被 host 的 `pricing.ts` 与 browser 的
  `client/pricing/draft.ts` 共同 import——「整点 / 星期几 / 时段冲突」三套规则若各写一遍,
  漂移的代价就是「草稿认为能存、写入被拒」。
- **旧文件不用迁移**:纯日期 `from` 继续合法(= 当天 0 点),没有 `slots` 的价段与今天逐字节
  相同;要迁移的只有派生的 `rollup.json`(费率行身份多一维,`ROLLUP_SCHEMA_VERSION` 3 → 4,
  旧折叠读作缺失、由日文件重建)。

**影响与已知取舍。** 时段**按本地时区**判定(与账本按本地日历日分区一致);分钟不是这条时间轴
的单位(`T12:30` 一律拒绝,界面走整点步长);时段不跨日,「22:00–次日 6:00」只能写成两段。

**界面规格**(卡片与费率格的尺寸、行状态记号、编辑态、触摸目标、对比度与复盘依据)见
[`docs/DESIGN.md`](DESIGN.md) §3.1——那是设计推理,不再抄回这里。契约见
[`docs/CONTRACTS.md`](CONTRACTS.md) 的「术语」「Host 路由」「数据目录」「让数字保持诚实的
不变量」四段;形状与规则见 `src/price-format.ts` 与 `src/pricing.ts` 顶部模块注释。

### D-014 · 2026-09-11 · 额度卡先判「什么在管这个账户」:订阅门 vs 余额门

**Status: current** · supersedes: D-003, D-012 · superseded-by: —

取代了 D-003 / D-012 里「额度卡只分 `ok` / `unconfigured` / `error` 三态、`ok` 一律按套餐窗口
渲染」的隐含前提(官方端点、只读快照、告急点语义都不变)。

**背景(维护者问)。** 「订阅额度 tab 存在套餐可能过期的问题。过期了应该怎么展示?还需要一直
查询吗?」查 [官方文档](https://commandcode.ai/docs/resources/pricing-limits)后事实变了:
5 小时 / 每周窗口**只约束订阅内含的月度额度**;官方原文「usage with **no subscription**
(free or balance-only) … **gated only by their credit balance**」「once your monthly pool is
spent — requests **skip the window check entirely**」「you're never hard-stopped」。套餐表里
**Provider $15/mo 的 Credits 一栏就是「Pay as you go」**——「没有订阅」是一种正当的付费形态。
[FAQ](https://commandcode.ai/docs/troubleshooting/faqs):订阅额度不滚存、**到期作废**,而
**已购/赠送额度滚存且永不过期**,且「Can I subscribe every other month? Yes.」——隔月订阅是
官方用法,失效是常态而非边缘情况。

于是旧行为在两个方向上都错:① 过期后接口仍回 200,`status` 非 active + credits 归零 → 仍判
`ok`,渲染出一张**绿色 0% 的卡**,subtitle 写「GOAT(canceled)」,本月额度行还会按
`periodEnd` 算出「即将重置」——把「套餐没了」画成「额度充裕」;② 拉取/已购/赠送三个余额字段
**拉了却从不显示**(全仓库唯一消费点是 `allowanceState` 只读 `monthlyUsd`),而余额正是失效后
唯一决定能不能继续用的数字;`monthlyUsd` 缺失时 `spent + 0` 还会算出 100% 红色「已超限」。

**决策。**

- **先判门(`QuotaGate`),再谈数字**。`ok` 卡带 `gate: 'subscription' | 'balance' | 'none'`
  (缺省 = `subscription`,与旧读法一致):`subscription` 由月度池 + 两个滚动窗口约束;
  `balance` **只由余额**约束;`none` = 没有生效订阅、且该端点**也不报余额**(OpenCode Go 只报
  窗口百分比)→ 这张卡没有任何能诚实上屏的数字。判定是纯函数 `quotaGate(planInfo)`,放 host
  (唯一跟官方接口说话的地方),client 不重算状态词表也不自算时钟。
- **每个通道用它自己的权威信号判**,不靠猜:
  - **Command Code 按「是否在期」**,不硬编码状态词。官方口径「cancel before your renewal
    date … stays active until the end of the current billing period」意味着 `canceled` 可能
    **仍在期**——所以 `active`/`trialing` 之外一律**以 `periodEnd` 为准**(未过期即
    `subscription`)。未知状态词因此退化成日期规则,而不是退化成一张错卡。实证:两份打同样四个
    端点的公开实现(`pi-commandcode-provider` 的 `src/quota.ts`、DSH 的
    `dsh-commandcode-usage-monitor`)**都没有做状态词映射**,没有可抄的词表——按日期判反而更稳。
  - **OpenCode Go 按 HTTP 语义**:它的用量端点不报套餐身份、不报日期、不报余额,唯一可用信号是
    状态码。端点自己的参考实现(cc-switch **#6433**,本仓库代码注释里引的就是它)写明「**403 =
    valid key, no Go subscription**(Zen 与 Go 共用 workspace key),与 401 鉴权失败是两回事」
    ——所以 401 仍是 `error`(key 本身要修),**403 改成 `ok` + `gate: 'none'`**:官方给的是
    **状态**,把它记成「查询失败」会让用户去查网络。注意该端点没有可替代的余额,所以 Go 走
    `none` 门(面板),而不是像 Command Code 那样换主体为余额。
- **门只从「真的答复了」的端点推导,绝不从失败推导**(审查发现并修掉的两处)。`status` /
  `periodEnd` 只存在于 `billing/subscriptions` 响应里,所以那条并行请求超时/5xx 时我们**不知道**
  套餐状态——若照旧推成 `balance`,就会对一个可能仍在订阅期内的账户说「未检测到生效中的订阅」
  并隐藏它的窗口(改动前是正常渲染窗口,属于回归);此时**不设门**(缺省 = `subscription`),
  下一次刷新自然会答。同理,`balance` 门承诺了一个余额,而 `billing/credits` 也没答复时
  `balanceUsd(undefined)` 会渲染成 `$0.00`——那是我们从没收到过的数字,故降级为 `none`。
  一句话:**门表达的是权益在不在,不是数据在不在。**
- **余额门换主体,不是清空**。窗口行**隐藏**(对不再受其约束的账户显示进度条是伪造约束)、
  表盘**不画**(余额没有分母,画百分比必是假读数),改为余额领读 + 三个来源逐项列出
  (`月额度 / 已购 / 赠送`)。
- **没有数字可放时就只出状态**。`none` 门不领读任何数值(窗口读数是 0% 会被读成「额度充裕」,
  而订阅根本不在),只出状态面板 + 恢复方式;文案**不武断说「已过期」**:无 `status`、无
  `periodEnd` 的按量账户没有过期,只说「未检测到生效中的订阅」,Go 的 403 说「key 有效但没有
  生效中的 Go 订阅(未订阅或已过期)」。
- **非订阅门不再自动刷新**。这类状态是终态:值不会自己变,唯一变化来自用户续费/充值——而恢复
  检测本来就有路径(这类卡仍是 `ok`,**照常落盘**;上次 `ok` 快照瞬时渲染,`fetchedAt` 一旦超过
  新鲜度预算,客户端在**打开 tab 时**就会强制刷新一次)。因此「打开即查一次」保留,停留期间按
  5 分钟捶一个「窗口已不适用」的账户则删掉。手动刷新按钮不变。
- **失效的卡排到最后**。tab 先展示还能花的套餐:已确认非 `subscription` 门的卡沉到其余之后。
  实现是**稳定分区**(`orderQuotaProviders`),host 给的显示顺序是组内顺序,所以除「下沉」本身
  之外不会重排;还没拿到结果的卡按在期处理——不拿「数据没到」当「已失效」,与门的判定同一条原则。
  顺序由各卡自己上报的门推出(client 侧,因为每张卡独立拉取、真相是一张一张到的;host 的列表
  是静态无网络的)。
- **告急点对非订阅门静默**(`isQuotaAlert`):窗口不再是约束,残留的 `exceeded` 不该点亮点。
- **连带修同源缺陷**:已购/赠送额度始终可见;`/alpha/usage/summary` 显式带
  `since=<currentPeriodStart>`,让花费与它对照的额度池**同属一个计费周期**(`settings` 文档与
  参考实现都这么做;实测 `周期花费 + 剩余池 ≈ 套餐月度额度`)。

**影响。**

- 契约:`QuotaCard` 增 `gate?` / `gateNote?`,纯函数 `quotaGate` / `balanceGateNote` /
  `dayText` / `noSubscriptionCard` 进 `src/quota.ts`;UI 与告急点规则见 CONTRACTS「Host 路由」
  「不变量」两段。
- **派生状态是读时计算的,不是存储的**:`gate` 由 host 每次拉取时按当次响应导出(Command Code
  看 `planInfo`,OpenCode Go 看状态码),所以磁盘快照与内存 TTL 卡都不需要版本迁移,续费后也不会
  被一张写死的「过期」掩盖——代价是每次打开 tab、每通道一次查询,这是恢复检测本身的成本,不是浪费。
- **Go 侧已知缺口**:该端点只报窗口百分比,不报 Zen 余额,所以 Go 走 `none` 门(只有状态,没有
  数字)。若将来要像 Command Code 那样显示余额,得另找 Zen 的余额来源——别人的实现是靠
  workspace id + 登录 cookie 抓控制台页(`pi-go-bars`),不是这条 API;本次不做。
- 已知取舍:`past_due` 这类「可能仍在服务」的状态按日期判(有未来 `periodEnd` 即显示额度),
  证据不足时按对应门显示(原始状态词照写进句子);不为它加「告警但可用」的中间态。
- 明确**不做**:后台探测过期(延续 D-012「告急点绝不后台打官方 API」)、本地时钟推断套餐过期
  (日历会撒谎,且只能省掉强刷前那 1 秒的旧读数)、为余额加告警阈值(没人要求)。

### D-017 · 2026-09-12 · 没写生效时间的价段锚在「首记」

**Status: partially superseded** · supersedes: — · superseded-by: D-019

本条末尾提到的轴渲染(轴外边界的 `◀` + 空心点、无首记时的回落左端)已由 **D-019** 取代;
锚定规则本身(没写 `from` 的价段按 `firstAt` 所在整点填)不变。

**背景(维护者原话)。** 「这一行的价格,没有生效日期,将其生效日期改成首次记录 tokens 的时间。」
维护者贴的是 `deepseek-official / deepseek-v4.1-flash-expires-on-0910` 那一行——它其实**已经**写着
`from: 2026-09-08`(首记 09-08 19:07,同一个日),所以真正要的不是改一条数据,而是一条规则:**凡是
没写生效时间的价段,都按这条模型首记那一刻填**。D-016 刚把「无起点」做成一等状态(左缘渐隐的开放
区间),它在**没有账**的行上是诚实的,在有账的行上却把「这份价从什么时候起算」留给读者猜:那段价
实际只可能管到首记之后,却不写任何日期;D-015 又明确不许行上借账本的时间说话,于是这一行的时间
只剩一句状态,说不出日期。

**决策。**

- **一条规则、一个实现**:`anchoredRow`(`src/client/pricing/draft.ts`)把该行**最早那一段**没写的
  `from` 换成 `firstAt` 所在**整点**(`instantKey`)。`''`(无起点)只在两种情况下留下:这一行**没有
  首记**(账本没记过这条串),或**另一段价已经起在首记之前或同刻**。
- **为什么是整点、为什么安全**:时间轴的单位是整点(D-013),而整点**向下取**保证锚点 ≤ 首记
  (`instantKey` 丢掉分钟)。首记之前本来就没有这条模型的账,所以锚定后覆盖的记录与「最早一段」
  **完全一样**——金额一分不变,变的只是它终于写着一个日期。取「日」会多覆盖几个小时(无害但更粗),
  取整点向上则会凭空造出一块「未覆盖」的空洞(有害)。
- **段序是硬约束**:锚定不许把这段价挤到其它边界之后,否则同一批账会改由**另一段价**计费——那是改钱,
  不是补日期。所以只要首记之前已有边界,规则主动放弃、保持无起点。
- **落在 browser 侧、只落在草稿上**:锚定值就是文件里的 `from`,与行、抽屉、时间轴共用同一份草稿;
  host 的读路径、计价口径、成本层一行都不动,也**不在读时写盘**——文件仍只在用户改动后整表落盘,
  锚定值随第一次保存落地,自那以后它就是一段普通的手写价。规则挂在**所有改动**的咽喉点
  (`PricingPanel.updateModel`)上,未定价行上敲下第一个数字、抽屉里清空生效时间,都汇入同一处。
  `baselinesOf` 改为从 `draftFromView` 取签名(基线不再自己拼一遍行),所以这条规则不可能让刚播种
  的行显示「未保存」。

**影响。** 纯 browser 侧改动:`docs/CONTRACTS.md` 记下这条草稿规则;D-016 的「左缘渐隐」分支保留,
只是变成少见状态(没有首记的行,以及首记之前已有边界时)。时间轴的左端随之**也改用整点**
(D-016 的第二次修订):锚点与左端因此是同一个时刻,第一段落在轴上、帽上写着它,不再需要
「`◀ 日期` + 空心点」去解释那几十分钟;`◀` 留给真正早于左端的手写边界。

**两条代价,都记在这里。** ① 有账的行上「自始生效」不再能从界面上表达(手写的 `from` 省略仍被
成本层读成自始生效,但下一次保存会被锚定值取代);要覆盖更早的历史,只能自己填一个更早的日期。
② 若日后回填进来一条**比首记更早**的记录(同步旧会话),它不再被静默按该段价计费,而是落到时间轴
的「未覆盖」块上并计数——这正是 D-016 建那块区域要它说的话,代价是它从此真的会出现。

### D-019 · 2026-09-12 · 调价史轴重做成「首记 → 今天」之间的节点轴

**Status: current** · supersedes: D-015, D-016, D-017 · superseded-by: —

取代 D-016 与 D-017 里**这条轴怎么画**的部分——每段价一块区间条、下排状态标签、「未覆盖」
区块、轴下说明句、`◀ 日期` + 空心点、没有首记时的回落左端,以及 D-015 那条轴下的说明句。
D-016 的其余决策(**左端锚在首记**、界面改用「无起点」、host 的账本透镜)与 D-017 的
**锚定规则**都不动。

**背景(维护者原话)。** 「大幅度[改]价格表的时间轴展示,移除冗余内容。现在,时间轴左端固定是首记
日期,右端固定是今天。在这个区间内生效的调价时间点,以节点的方式展示,每个节点上方标注日期。
节点之间存在最小空间间隔,避免拥挤。」追问后确认六点:① 节点**按日期比例落位**,靠得太近时按
最小间距摊开(两端固定、不横向滚动);② 「冗余内容」= 区间条、下排状态标签(当前生效 / 未生效 /
峰谷 N 段)、「未覆盖」区块、轴下说明句,**全部删掉**;③ 区间之外的时间点(早于首记的边界、今天
之后生效的段)**都不上轴**;④ 没有首记的行**不画轴**;⑤ 「当前生效」保留**视觉**提示(强调色圆点),
只是不再有状态文字;⑥ 这次只动界面,host 照旧下发 `unpriced` / `lastAt`,不趁这一轮删 wire 字段。

**决策。**

- **轴上只有节点**:一次调价 = 轨道上一颗点 + 点**下方**的日期,左端印 `首记 <整点>`、右端印「今天」
  (各自贴住轨道两端)。当前生效那颗点用 `--dtpl-accent` 且 6px(其余 5px)——状态不只靠颜色,而
  那些文字本来就在行内四档价、行尾徽章与下方价段列表里。
- **比例落位 + 最小间距**:节点按 `(时刻 − 首记) / (今天 − 首记)` 落位,相邻标签净距不足 6px 时
  向后摊开——**比例因此局部失真**,轴读的是调价的**先后**而不是距离。两端钉死,轴**永不横向滚动**:
  真放不下时压缩间距,而不是把两端推出视野或让日期叠在一起(约五个节点以内都能各就各位)。
  标签宽度是**估算**的(`labelWidth`:9px 下等宽数字实测 ~0.49em、CJK 1em,故意取 0.52em 偏宽
  一侧——估宽只是多留几 px 空隙,估窄才会把两个日期叠起来;实机量过 `2026-09-10 12:00` = 69.8px)。
- **轨道宽度是量出来的**(`ResizeObserver`):最小间距是 px,百分比在窄抽屉里保证不了两个标签不叠。
- **区间之外一律不画**:边界早于首记(那一刻它已在生效,但那次「变化」不属于这段历史)、`from`
  省略的无起点段、今天之后才生效的段,都只在下方价段列表里出现。**恰好在首记那一刻生效的段折进
  左端**:同一个时刻只印一个日期(左端的那个),那颗点仍归属该段、仍可点。
- **区间里一个节点都没有就不画轴**(维护者在实机看到两类空轨道后确认):(a) 有价但调价全在首记
  之前(如 `deepseek-official/DeepSeek-V4-Flash`,价写 08-01、首记 08-15);(b) 整行没价(订阅通道
  的价格未知行)。一条只有两端的空轨道说不了行内四档价与下方列表没说过的事。
- **右端取渲染那一刻的 `now`**,而不是当天 0 点:今天之内、但还没到点的调价因此天然落在区间外
  (它还没生效),不必再加一条「未来段」规则。
- **轴拆成纯模块**(`src/client/pricing/axis.ts`:`axisNodes` / `labelWidth` / `placeNodes`),
  `pnpm smoke` 直接测不变量:两端钉死、顺序不乱、放得下时保住最小间距、放不下时也不越界。

**同日追加(维护者原话:「把时间轴加粗,节点日期移动到时间轴下方」→「首记时间 和 今天,两个端点,
还是放置在时间轴上方」)。** ① 轨道 1px → **3px**(2px 实机截图仍偏细,与 5px 的点不成比例;4px
则像一条色带,点几乎被吞掉),圆角 1.5px;② 轴的**三行**从此定型:上排只有区间的两个端点
(`首记 <整点>` 与「今天」),中间是轨道与挂在轨道上的点,下排是各次调价的日期。也就是说
**节点日期一律在轴下方,端点的名字在轴上方**——两端命名的是区间的边界、不是某一颗点,分开两排
之后它们也不会与相邻节点的日期争同一行的宽度。点仍居中于自己的标签,估宽与最小间距的算法一行
未动(它照样为端点标签预留横向空间)。定位值随之整体重排且同心不变:轨道 `top:17px`/`height:3px`、
点 `top:16px`、当前生效点 `top:15.5px`(三者中心都在 18.5px),调价日期 `margin-top:24px`
(占 24–36px),端点标签留在节点头部(0–12px),**轨道总高 24 → 36px**(按钮的点击高度随之变高)。
③ 顺带修掉一个被这次改动**照出来**的老毛病:节点若是 `<button>`(端点上也挂着一段价时),
`<button>` 的 UA 布局会把内容盒垂直居中,端点标签因此比 `<span>` 端点低 12px——修法是让按钮成为
列向 flex 容器(`display:flex;flex-direction:column;justify-content:flex-start`),三种候选的实测
记在 `docs/LESSONS.md` §7。

**影响。** `Timeline.tsx` 与 `styles/pricing-timeline.ts` 重写(`.dtpl-tl-*` 只剩轨道 / 节点 /
圆点,不再借用台账趋势图的条形语言);新增 `src/client/pricing/axis.ts`;`scripts/smoke.ts` 新增
一节。文档:`README`(价格表一节)、`docs/CONTRACTS.md` 的账本透镜段同步,本条目取代 D-016 / D-017
的轴渲染部分(两处状态行已标注)。

**三条代价,都记在这里。** ① 「有价的行也有没价的账」不再有地方说——D-016 建的「未覆盖」区块是
它唯一说这句话的地方,维护者明确接受(整行没价仍有「价格未知」徽标);② 密集调价史(约 5 个节点
以上)会看到标签彼此靠近,不再有横向滚动这条路;D-016 记过的备选(标签缩成 `MM-DD`)仍在桌上;
③ `unpriced` / `lastAt` 从此没有界面消费者(仍在下发、CONTRACTS 照旧描述),删不删留到下一轮。

   只有两个 tab 标签、而标签说的是**切法**不是这一节是什么);通道由列头命名,行内不再重复
   「通道」;轨道同时取代行分隔线,一行从两条横线减到一条。窄屏按价格表先例收掉列头、改单列堆叠。
   列头**一行**写(「模型 · 通道」/「词元 · 金额」):它最早照数据的**两行**写成两行,标签能精确
   落在各自数值正上方,但四枚孤零零的标签占两行、中间大片空白,表头比它标注的数据还高——维护者
   一眼看出「这里有双层」。改一行之后 41px → 27px,牺牲精确对位换回它像一行表头。
   随后按 ui-ux-pro-max 的规则复查了一遍,又收了三处:① **只限不可预测的那一半**——桶名
   是固定的一段字,给它 nowrap + min-width(而不是硬 width,硬宽在字体变宽时会折行或被裁);
   限宽 + 省略号 + title 留给数额。② **补回读屏的列名**——上一版把行内「通道」与表头一起
   aria-hidden,等于从无障碍树里删掉了「commandcode 是什么」,现在每个格子自带一枚 `.dtpl-sr`
   列名。③ **明确不给行加 hover 底洗色**:行不可点,hover 反馈在交互元素上才成立,静态行加它
   是假的可点承诺(触屏也触发不了)——这一条推翻了本条目起草时的设想。**后续补一处**:上面那枚
   「订阅价值」槽位原本在现金行里用 `visibility:hidden` 藏着(只为占位对齐),于是工作区行出现
   「¥3.28 · ¥0.60 订阅价值」——同一格里一个数有名字、另一个没有,维护者指认**读不出前者是哪个
   桶**。改法:槽位**永远填着该行金额的桶名**(现金行写「实际支出」;两枚名字都是四个汉字、同宽,
   所以金额右边缘照样只剩一个值);工作区跨通道、两桶可同时非零,那就是金额格里的**两段**并排
   (各自带名,段间走这个窗口的 `·`),`is-blank` 这条规则随之删除,金额列改按这一列里最宽的
   那种内容定宽(200 → 224px;按模型行一段只占 ~90px,多出来的只是留白)。
   **后续补一处(排版)**:同一面还收了两处行内落差——失败数拿 `--dtpl-warn-ink` + 600(请求数
   是读数,失败是这一行唯一「要看一眼」的状态,与 hero 今日异常行同一个 token),「未归属」用
   一条发丝线 + 次要色标题标成对账行(D-018 明写它不是项目、不参与「最近有操作在前」),
   行内其余排版一字不动。工作区行因此与按模型行同高(54px)、轨道同节奏。

**依据:金属为什么是 1px 而不是一层渐变。** 终末地的底材是「金属、管线」,而它在界面上最省的表达
不是把面板刷成金属色,而是**机加工面在受光边的反光 + 背光边的投影**:`inset 0 1px` 白 7% +
`inset 0 -1px` 黑 12%,固定黑白,不随主题翻转。于是深色面上只有顶部亮线可见、浅色面上只有底部
暗线可见,同一套材质在两个主题各自成立。它叠在 1px 硬边框**之内**:外轮廓与材质是两件事,上一版
正是让一条半像素阴影同时充当两者才糊掉的。

**依据:母题要匹配它占的那块地方,这一条比「把图形画对」更靠前。** 那个 SVG 路径本身没有错——同一
个 h 只有一个水平集,所以线永不相交、线宽恒定、疏密随坡度自己变,放大到 4× 确实是一张地形图。
它错在**位置**:hero 里唯一空着的是右上角一条带子,而它被金额块顶死——金额块**有两行**(实际支出 +
订阅价值)、底对齐在口径词那一块,实测两行时顶边落在 hero 的 45px 处(一行时 63px),所以带子最多
38px 高。等高线硬解进 240×38 就退化成几根近乎平行的短弧。**等高线只在「线足够多、能围出闭合的圈」
时才读成地形**;几条互相不搭界的弧读起来就是「孤零零的几条线」,比不画更糟。第一版按 58px 做还压到
过金额上——一行金额看起来更空,但那是「今天没花钱」的偶然态,不能按它定尺寸。
换母题之后有两条约束值得记下来:① **刻度轨整条落在 hero 的下内边距里**(轨顶 = hero 高 − 4 − 9),
所以最高的那层刻度也碰不到「累计」那一行;② **刻度的黄必须省掉**——黄是「料」不是「线」,1px 的黄在
白底上只有 1.57:1,做刻度线会直接消失,黄在这一屏只留给口径词那枚徽记(仍在「三处」预算之内)。
沿用的实测结论:同一个 alpha 给不出跨主题一致的重量(合成在 sRGB 空间、对比度按线性亮度算),
所以任何「按透明度画线」的东西都得按主题分档——`--dtpl-warn-ink` 与已删掉的 `--dtpl-contour-ink`
是同一类问题。

**取舍。** ① **顺手修掉两处真实缺陷**:四个 tab 的数字漏了等宽(全窗口唯一一处比例体数字,而价格表
固定列的可比对性本就以等宽为前提),补上等宽后费率列宽必须按最宽字体重推 → 64px 改为 **74px**;
`--dtpl-warn` 作 11px 正文只有 2.15:1 的老问题在额度芯片 / 暂存提示 / 未生效徽章上仍存在,一并换
`--dtpl-warn-ink`。② 焦点环继续跟随 `--dtpl-accent`:焦点是**系统信号**,不是这套视觉语言的一部分。
③ 收掉虚线接缝、accent 渐变与 accent 染色 chip——全窗口不再有虚线、渐变与身份色分类。④ 品牌黄的
预算**没有扩大**,仍是当前页 / 峰值 / 徽记三处;「未保存」与「订阅」改用实心墨芯片而非黄,刻度轨
也走墨色。⑤ 本轮只碰 `src/client/styles/**` 与 hero 里那一个装饰元素(纯呈现,不动契约);**轴的
刻度点**顺手改直角——它和趋势图的柱同属数据图形,真正保留的圆仍是侧栏按钮 / 状态灯 / 额度表盘三处。
⑥ 等高线**整个插件里都不再出现**,那条 731 字节的生成路径与 `--dtpl-contour-ink` 一并删掉了;
另一条备选(把它铺满整块 hero 当低对比度底纹)也试过并出了图,能保住签名、代价是纹理从数字底下
穿过,维护者选了结构件这条。

黄牌与加粗标签保住形与品牌落点;这是刻意的减重,不是撤销高亮。70% 是量出来的:82% 时柱体与恒定的黄
明度几乎相同(对深底 9.4:1 vs 9.0:1),黄牌挨着浅块也读不出来;70% 时柱体约 6.9:1,仍是全图最亮的
一根(其余柱 3.9:1)。**同一窗口、同一量法**:可见黄 3709px² → 67px²(−98%),其中 55px² 是节徽记
自己的边缘,牌面只剩 12px²(4×8 被 1px 墨边吃掉一大半)——黄在这一屏已接近「只作为记号存在」。
② 若要恢复更强的峰值信号,正确的方向是**回收别处的黄**(节徽记降为墨块,让黄在整屏只出现一次),
而不是把黄重新铺回这根柱。

**取代 D-025 / D-028 的一部分。** 不再成立的是 D-025 的「峰值柱 = 黄填充 + 墨边」、它取舍段里「峰值柱
的墨边在深色主题下几乎看不见」(柱体取 70% 之后,浅块上的墨边在深色主题里读得出来),以及 D-028 代价段
里「峰值仍由黄块 + 墨边 + 加粗标签表达」;两者的其余规则(黄是「料」、三处预算、撤掉峰值参考线)继续
生效。

## 如何追加条目

1. 在**文件末尾**追加 `### D-NNN · 日期 · 标题`。标题会被索引表逐字复用,所以写短语,不写句子。
2. **状态行照抄这个格式**(`scripts/selfcheck-docs.ts` 会校验,写错当场红):

   ```
   **Status: current** · supersedes: — · superseded-by: —
   ```

   `supersedes` 列出**本条取代了谁**,`superseded-by` 列出**谁取代了本条**;多个 ID 用 `, `
   分隔,没有就写 `—`。取代关系必须**双向**:你写了 `superseded-by: D-021`,就要去 D-021 的
   `supersedes` 里写上本条。
3. **一条 ≤ 40 行**(`docs/WORKFLOW.md` §7):背景、决策、代价与取舍各一段,指向
   `docs/CONTRACTS.md`(契约)与 `docs/DESIGN.md`(更深的推理),而不是把它们抄一份。
4. 若是 `current` 或 `partially superseded`,在顶部索引表加一行——不进表 `selfcheck` 会失败;
   纯 `superseded` 的条目反倒**不能**进表。
5. 若新决策取代旧条目,**把旧条目的状态行一起改**(降级状态 + 双向链接)——与代码同一 commit。

### D-030 · 2026-09-15 · 读路径不再 await 权威同步(后台自愈 + 15 s 节流)

**Status: current** · supersedes: — · superseded-by: —

**背景(维护者原话:「通道用量和价格表 tab 打开怎么要加载半天,修复这个bug」)。** 实测把这句
坐实了:真实账本 5.6 MB / 20.6k 行,`/tokbook/usage`、`/tokbook/pricing`、`/tokbook/overview`
在**不挂 sessionPersistence** 的读取路径上分别是 42 / 23 / 72 ms(热缓存 11–77 ms),所以慢的
不是账本读。慢的是**每次读都先 await 一次权威 walk**:新鲜度探针在当前会话上永远报 stale
(它每来一条消息就换一次 revision),而 walk 对该会话**整份日志重读重折叠**——本机
`~/.dsh/sessions` 有 251 份会话日志、208 MB(最大单份 8.6 MB 压缩、数万事件)。于是每打开一个
tab 就付一次秒级重读,而且那些行**早已**由 `session/event` 实时 hook 记进账本了。

**决策。** ① 读路径的探针只做廉价部分(列会话 + 比对 revision),需要折叠时把 walk **排到后台**,
读立刻返回账本当前内容;② 后台 walk 按 **15 s** 节流(已有基线的漂移会话),避免持续重读那份大
日志;③ **没有基线签名的会话不受节流**(首次回填、刚开的新会话——便宜且该立刻同步),这是自愈路径
保持活着的关键;④ 唯一的例外是**冷账本**(一个日文件都没有):那时读路径等一轮,否则首次安装 /
换数据目录会把「还没回填完」显示成「没有记录」;⑤ `doSync` 的日志行加上**耗时 + 会话数**,
使这类成本下次能从日志里直接看出来。

**代价(明说)。** 账本可能比持久化日志晚至多一个节流窗口(15 s)——实时 hook 覆盖当前会话,
所以实际可见的滞后只落在「别的进程写下的行 / 折叠曾经失败」这两种情况上,而那正是 walk 的
职责;**重新扫描**按钮仍旧立刻走一遍全部会话(它的语义就是权威重来,不受节流)。冷启动的
首次回填也仍旧可能很慢,但那时账本没有内容可显示,等待是唯一能给出正确空态的做法。

**验证。** `scripts/selfcheck-readpath.ts`(进 `pnpm selfcheck`)用 `inspect()` 慢 400 ms 的
persistence 桩钉住四条不变量:三个读都必须 < 150 ms 返回、walk 仍会跑完、漂移会话被节流、
无基线会话不节流;并单独钉住冷账本等一轮的例外。同一个脚本在旧行为(读里 `await doSync`)下
第一条即 FAIL(实测 413 ms),所以它是真的回归测试,不是装饰。
