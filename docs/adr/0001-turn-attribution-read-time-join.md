# ADR 0001 — 会话词元页的轮次归属走读时 join，不写进账本行

> **Doc meta** · role: reason · language: zh-CN · status: current · last-reviewed: 2026-09-27 · supersedes: —

- **状态**：已接受（2026-09-27）
- **决策**：新增的「会话词元」页要按轮次/步骤分组时，**宿主在请求时读该会话的持久化日志**，把账本行按 `requestId` join 上 `(turn, step)`；**不给账本行加 `turn`/`step` 字段**。

## 事实（决定这条的原因）

- **日文件只追加、绝不重写**（[`CONTRACTS.md`](../CONTRACTS.md) §3）。因此任何写进账本的字段都只能覆盖**此后**的行。
- 账本里此刻已有约 **3.9 万行 / 358 个会话**的存量行，它们不可能回头补上轮次。
- 轮次与步骤**本来就在事件里**，不需要重新推导：`assistant/message` 带 `turn` + `step` + `usage`，`llm/retry` 带 `turn` + `step`，`turn/end` 只带 `turn`，`compaction/summary` 两个都不带。
- 宿主已经有一条只读通道：`sessionPersistence.open(id, 'read')`，其 `read` **不取写所有权**，与正在写的宿主并行安全（`src/sync.ts` 已经在用，并且跳过 `inheritedEventCount` 的父会话前缀）。
- 所以 join **不是**在第二处重写轮次折叠逻辑：它只是把 `requestId` 映射到两个现成字段。唯一需要小心的是压缩行——它归「轮间」，见 [`CONTEXT.md`](../CONTEXT.md)。

## 被否决的方案

- **把 `turn`/`step` 写进账本行**：行会更自包含，任何未来的视图免 join。但 append-only 意味着**历史行永远显示「轮次未知」**——同一张按轮次的表里会长久并存两代格式，而「补上历史」这件事在写入侧无解。代价换来的便利（免 join）本页本来也要付：为了钱，账本无论如何都得读。
- **两者都做**（新行写字段、历史读时 join）：同一事实有两个来源，页面上必须自己跟自己对账，正是本插件要避免的那类口径风险。

## 后果

1. **token 与钱都取账本**，轮次/步骤只是 join 出来的归属。不采用 DSH 的 `tokenUsage` 投影来提供 token——它与账本会在边界情况（漏记的行、refile 时序）分叉，而「同一个数字两个来源」是账本这一层的红线。
2. 会话日志读不到时，那批行显示**轮次未知**，既不猜、也不按时间硬塞进某一轮。这与「用量未知 ≠ 0」同一条思路：未知要**说出口**，不能默默变成 0 或「轮间」。
3. join 的成本随该会话日志增长；按仓库已有的**「按文件版本判新旧」解析缓存**模式缓存（分日文件解析缓存是同款做法），刷新时不必每次重解。
4. 账本行格式不变：去重键（`requestId`）、费率行身份、`ROLLUP_SCHEMA_VERSION`、refile 与计价口径**一个都不动**。
